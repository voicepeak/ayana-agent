# 上下文管理审查 · 2026-10-06

审查对象：当前工作目录源码，包含已有未提交改动。没有修改业务代码，没有调用真实模型、读取个人聊天数据库或操作外部应用。以下复现使用临时目录、测试桌面/静音语音替身与 httpx.MockTransport。结论针对源码，不代表已发布 EXE 的运行状态。

## 当前上下文如何工作

在线模型请求按以下顺序组装（`services/agent/runtime.py:564–581`）：

1. 系统提示：人设、语音格式、事件协议、任务协议、权限、工具说明、表情规则。
2. 当前仓库概览：文件列表和少量入口文件内容，作为独立的 user 证据消息。
3. 本话题摘要及保留的完整模型轮次。
4. 当前 user 消息：问题、模式、目标、时钟、目录授权、任务/文件引用、表情上下文、上一轮播放回执、中断回复等 JSON。
5. 可选当前截图；工具往返时继续追加 assistant 调用、tool 结果或 user 结果消息及新截图。

上下文状态分散在多个存储中：

| 状态 | 位置 | 用途 |
| --- | --- | --- |
| 界面聊天记录、工具事件 | SQLite `events` / `utterances` | 历史页、显示和播放回执 |
| 模型原始完整轮次 | SQLite `model_turns`，内存 `PromptHistory.turns` | 下一次模型请求的事实历史 |
| 本话题摘要 | SQLite `context_summaries` | 替代较早的完整模型轮次 |
| 任务、文件和来源引用 | conversation 记录内 `work_context` | 接续工作，最多 8 个未完成任务和 16 个对象引用 |
| 管理页任务状态 | SQLite `capability_records(kind=task)` | 管理页、启动时标记中断 |
| 正在进行的任务、工具证据、确认后的续跑消息 | `active_task` / `continuation` 内存对象 | 当前轮执行及完成核验 |

`conversation_id` 是主要历史隔离键；换模型不会创建新话题。`session_id` 标识进程会话，generation 用于取消旧输出。历史与播放回执分离、按完整轮次摘要、摘要与剩余历史事务写入、默认不保留截图，均有合理目的。问题集中在这些状态的交接和容量控制。

## 已确认的问题

### 1. P1：失败或同话题取消时，没有封存已发生的模型轮次

位置：`services/agent/runtime.py:738–781`；话题切换特例在 `services/agent/conversation_runtime.py:86–98`。

模型轮次只在正常结束、没有待确认操作时 append。异常处理保存错误和任务状态，但不保存已经读取的工具内容与模型交换；取消分支直接抛出 CancelledError。切换话题有额外的中断证据补写，同话题继续发送消息没有同样的处理。

复现：模型先调用 `files.read` 成功读取 `proof.txt`，内容含唯一标记；第二次模型请求返回 503；用户再发“continue”。原问题仍在界面历史中，失败轮次不在 `PromptHistory.turns`，下一次请求没有文件内容中的唯一标记。

`work_context` 可能保留目标、文件路径、任务状态；中断补充可能保留最近生成的语句。因此问题是完整事实交换和工具内容丢失，不能概括成所有上下文都消失。若需要接续执行，模型必须重新读取，或只能根据残缺状态推断。重启会进一步丢失内存中的未封存交换。

建议：以话题与 turn_id 为键建立增量轮次账本，持久化已确认的用户输入、模型输出和真实工具结果；成功、失败、取消均封存状态。重放时保持完整的原生工具调用/结果配对，未执行的提议单独记录，不重放动作。

### 2. P1：预算只在用户新轮开始时检查，多轮工具调用可以持续超限

位置：`services/agent/runtime.py:578–579`、`:690–731`。

`_compact_history` 只在初始请求前调用。工具结果、模型输出和截图追加后，没有再次检查完整请求大小；确认后续跑也直接复用已有 messages。历史摘要不能控制当前尚未结束的轮次。

复现：同一任务连续七次通过真实 `files.read` 读取临时目录内 16,000 字符的 UTF-8 文件，最后正常回答。共八次模型请求，最大 messages JSON 为 **135,118 字符**；默认 `max_chars` 为 **64,000**；摘要请求次数为 **0**。无需构造无限循环或突破工具单次读取限制。

这些是字符数，不是 token 数；尚未实测特定线上模型是否拒绝此请求。已经确认的是项目自身的预算没有约束工具往返。增加允许工具轮数或单次材料大小会放大问题；本轮中多张截图也不会被历史的去图处理约束。

建议：所有主请求、工具续跑、确认续跑经过同一容量检查；预留实际输出上限、工具 schema 和图像成本。工具结果保留真实出处与可续读入口，超限时分段处理或压缩已经完成的交换。

### 3. P1：固定上下文过大且历史为空时，容量保护会漏过

位置：`services/agent/context.py:70–77`；`services/agent/conversation_runtime.py:29–46`。

剩余预算计算为 `max(0, max_chars - reserve_chars)`。代码先判断历史 size 是否小于预算，再判断预算是否低于 5,000。历史为空、固定材料本身超过 64,000 时，两者都是 0，直接返回“无需摘要”，实际超大请求仍会发送。

任务列表只有数量限制，没有总文字限制。8 个未完成任务，每个包含允许范围内的 4,000 字符 goal、resolved_goal 和 12 项完成条件，足以让当前固定消息独自超限。

复现：注入上述合法字段长度的 8 个待核验任务，空历史下发起新问题。messages JSON 为 **144,394 字符**，摘要请求次数为 **0**，模型请求仍发送。

建议：先验证固定部分能否容纳，再计算历史预算；限制任务状态和对象引用的总体积。当前消息只发送必要的活跃目标与未完成条件，其余通过可检索记录引用保留。

### 4. P1：摘要请求本身没有容量控制，也没有分批推进

位置：`services/agent/context.py:70–83`、`:115–139`；`services/agent/conversation_runtime.py:148–173`。

触发压缩后，会将所有选中的旧轮次、旧摘要和播放回执一次性交给当前模型。完整大轮次不会拆分，摘要请求没有独立输入预算；失败保留原文是正确的，但下次会再次尝试相同的大请求。

复现：保留一个含 140,000 字符内容的旧轮次，让摘要接口模拟容量错误。两次“continue”都只发送了同样大小的非流式摘要请求，messages JSON 均为 **140,426 字符**；没有发起主回复，原始轮次仍然保留。

模拟错误用于证明失败后的重复路径，没有证明线上服务在此字符数必然拒绝。对于容量不足或无法处理大摘要的端点，该话题可能持续卡在摘要步骤；开始新话题绕开问题，同时失去自然接续。

建议：给摘要建立独立输入预算，按已完成工具交换分批摘要，处理单个过大轮次，分批成功后可安全推进。保持摘要失败时原文不丢失的现有保证。

### 5. P1：文件引用缺少稳定仓库身份，材料切换后会指向另一份文件

位置：`services/agent/work.py:128–147`；`services/agent/tools/text_reader.py:47–49`；`services/agent/conversation_runtime.py:135–145`；`services/agent/runtime.py:304–310`。

文本读取结果只有 `root_id=repository` 和相对 path；对象身份也用这两个值。repository 实际解析为当前绑定仓库，引用本身没有保存当时的绝对根目录。解除材料不会失效这些引用，切换仓库也不会重新绑定旧对象身份。

复现：读取 repo-a 的 `config.py` 后保留其 work_context 引用；解除材料，再绑定 repo-b；用旧引用再次 files.read，实际返回 **repo-b 的内容**。旧引用在解除材料后仍存在。

因此，用户说“刚才那个文件”时，记忆中的引用可能被当前仓库解释成另一份同名文件。已复现错误解析和读取；没有执行错误写入。

建议：对象绑定规范化绝对根目录/文件路径、独立的 material_id 和读取版本。切换材料时将旧引用标为历史或不可用，使用前核验身份；不要仅依靠会动态变化的 root_id。

### 6. P2：重启恢复只修正任务表，没有修正模型所用任务状态

位置：`services/agent/runtime.py:106–109`；`services/agent/conversation_runtime.py:15–27`。

启动时把 task 记录的 running / paused / waiting_approval 改为 interrupted。但是 conversation.work_context 中的 current_task 不同步修改；只要 work_context 已存在，读取时也不会重建或核验任务状态。

复现：用持久化记录模拟退出前的 running 任务，重新初始化 runtime。任务记录为 **interrupted**，work_context.current_task 仍为 **running**，pending_tasks 为空。模拟的是已写入数据库的崩溃状态，不需要真实强制结束进程。

新轮创建的 current_task 会替换这个旧值，因此不能声称每次新请求都必然带 running；实际问题是恢复后的两套状态不一致，旧工作没有可靠转入可接续的未完成任务。

建议：启动时按话题统一恢复任务状态、取消未确认提议，并将可接续目标归入未完成队列。任务状态应由同一持久化记录派生，避免维护互相漂移的副本。

## 设计上的额外局限

以下是源码可以确认的能力边界或设计风险，区别于上面的确定性缺陷：

- 摘要是最长 4,000 字符的自由文本，系统要求尽量简短，没有结构化事实条目、来源引用或矛盾处理机制。反复摘要可能损失细节；本次没有对真实模型的摘要准确率作评估。
- 完整轮次中的每个 user 消息都保存当时的目录、目标、任务快照、播放回执、时钟和表情状态，后续原样重放。即时状态反复占用历史，并增加模型区分旧状态与当前状态的负担。
- 原始聊天/工具事件仍在数据库，但没有向模型提供按本话题检索历史证据的工具。进入摘要后，需要精确细节时，通常只能重读仍然存在的文件或网页。
- 截图从模型历史中移除符合当前保存策略，但没有自动提取可核对的视觉观察记忆。仅来自截图的信息不能靠文字历史完整恢复。
- 未实现跨话题个人记忆，项目文档对此已有明确说明；因此跨话题“应该记得我的偏好”目前不是已有保证。
- `events` / `utterances` 没有容量清理，选择话题时 model_turns 全部读取；故障造成的大轮次也会随话题加载。可以后续补容量生命周期，但不能通过删除原始证据来掩盖预算问题。

## 建议的修复顺序

1. 先补失败、取消、重启的轮次封存与任务恢复，让已经发生的事实可追溯。
2. 建立每次模型请求统一的容量检查，同时处理固定材料、当前工具轮次和摘要请求。可以先用保守估算，但不能只有历史字符裁剪。
3. 给文件、材料与工具结果稳定身份和版本，让历史引用不会跟随当前仓库漂移。
4. 再精简历史中的即时状态，提供本话题证据检索，最后完善结构化记忆和长期偏好。

目标结构可以沿用现有 SQLite 和模块划分：**原始事件/工具证据账本 → 活跃任务状态 → 本话题事实摘要与近期交换 → 统一请求组装及预算检查**。无需为此增加分布式服务。
