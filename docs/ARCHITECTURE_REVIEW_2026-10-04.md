# 缓存修复与架构审查 · 2026-10-04

## 结论与范围

当前分层适合单用户 Windows 桌面同伴：Electron 管窗口和 IPC，Agent 管模型与工具，TTS/STT 使用独立推理进程，原生桌面适配器负责观察和明确确认后的单步输入。无需为了缓存另建 Redis 或拆成远程微服务。

本次审查覆盖 Ayana 自有的 Agent、模型适配器、历史存储、协议、仓库工具、Windows 适配器、TTS/STT、Electron、React、播放器、构建和验证脚本。外部 GPT-SoVITS/Whisper、Electron 和 Python 依赖按接口与进程边界检查；未对外部引擎全部源代码或第三方依赖执行独立安全审计。工作目录同时出现的语音解码改动独立交付，不属于本次缓存修复提交。

模型缓存低的主要代码原因已经消除，真实 DeepSeek 对照支持改善。剩余问题主要是事件持久化、数据和图像容量、协议契约及发布可复现性；它们列在后文，不能将本报告理解为所有风险均已消失。

## 原因与最终实现

旧请求把当前问题和完整仓库证据放进一条结构化 user 消息。下一轮却用 SQLite UI 事件把它重建成普通字符串；assistant 原文被拆成逐句消息，键替换成运行时 ID，并混入 reception、played_samples。最近 16 条消息的滑动窗口还会不断改变历史开头。这些变化截断了可复用的前缀。

DeepSeek 缓存按重复输入前缀复用，服务端会异步生成和淘汰缓存，命中不是强保证；模型采样温度不是解决输入缓存的开关。[官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)。实际用量来自 API 的 usage，包括 prompt_cache_hit_tokens、prompt_cache_miss_tokens，也兼容 prompt_tokens_details.cached_tokens。[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)。

最终输入顺序为：

1. 稳定的角色、工具政策、协议和表情指令。
2. 一份稳定排序的所选仓库证据，作为不可信 user 数据。
3. 完整模型轮次：原始 user 结构、assistant 原文、工具请求和工具结果。
4. 当前模式、目标、快照引用、上一轮实际接收状态、中断输出补充和新问题。
5. 当前截图，仅在配置允许且存在截图时追加。

`PromptHistory` 与播放账本分开，完整轮次保存在新增的 model_turns 表。原始 assistant JSON 格式和事件键保持不变；实际播放/显示状态追加到新请求尾部，不重写旧消息。关闭历史保存时保留本进程内上下文，并用内存中的播放回执说明接收状态，不写入模型历史。

历史按模型地址、模型、完整系统提示和仓库根目录分区。上下文达到字符预算时，按完整轮次批量删除旧记录并腾出空间，避免每轮移动前缀。默认历史与固定文字输入共享 64,000 字符的保守预算，并预留回复空间；这是字符估算，尚不是基于各厂商 tokenizer 的严格 token 上限。

旧安装的显示/播放历史在首次升级时只迁移一次，冻结为初始上下文。原有 UI 历史保留。截图不保存到 model_turns，也不在后续对话重发；这会使包含截图的上一请求无法完整原样重放，但更早的文字前缀仍然稳定。当前截图变化、仓库证据变化、切换模型/提示/仓库、历史裁剪和服务端淘汰都可能产生合理的缓存失效。

Agent 复用一个 httpx 客户端，避免每轮/每次工具调用重新建立连接。设置页显示最近请求的输入 token、缓存 token 和比例；缺失 usage 时不会伪造零命中。这个数值是最近一次成功完成的模型请求，不是全账号账单统计，也不覆盖中断且未返回 usage 的请求。

## 真实 API 对照

脚本：`scripts/benchmark_prompt_cache.py`。使用已配置的 DeepSeek 模型与受保护凭证，对固定的三个短问题和仓库公开说明/源码证据比较旧历史重建与最终方案。使用临时数据库，不读取用户对话历史，不修改个人配置，不生成声音、不执行桌面输入；截图关闭。原始数字保存在忽略提交的 `.runtime/benchmarks/prompt-cache.json`。

| 路径 | 第 2 轮输入 / 命中 / 未命中 | 第 3 轮输入 / 命中 / 未命中 | 第 2–3 轮加权命中率 |
| --- | --- | --- | --- |
| 旧历史重建 | 5,894 / 768 / 5,126 | 6,042 / 896 / 5,146 | 13.94% |
| 稳定前缀与证据去重 | 5,956 / 5,760 / 196 | 6,146 / 5,888 / 258 | 96.25% |

连续两轮未命中输入从 10,272 降至 454 tokens，下降 95.6%；输入总量从 11,936 增至 12,102，增加约 1.4%。新结构的历史请求保持完整前缀；旧结构两次均不保持。第 2、3 轮首个 speech 的观测耗时为旧路径 1,141 / 1,063ms，新路径 734 / 829ms。样本太少，不能据此宣称稳定的延迟分位数或总体性能提升幅度。

最初尝试完整保存每轮包含的仓库上下文，虽改善命中率，却让证据在历史中重复，输入总量快速上升；最终实现已消除这个问题。最终比较关注未命中输入和总输入，不靠填充/重复提示来抬高命中比例。

两条路径共用账号/系统提示，先后顺序也会影响服务端缓存冷热，因此主要比较追加对话的第 2–3 轮。该实测是三轮文字请求的小样本，不能代表截图场景、长会话、缓存过期后的冷启动或所有模型。没有按价格表推算账单节省。

## 剩余问题与建议顺序

| 优先级 | 代码位置 | 具体影响与建议 |
| --- | --- | --- |
| P2 | services/agent/runtime.py: emit；services/agent/storage.py: commit | 同步 SQLite 写入、commit 和顺序 WebSocket 发送处于同一事件循环；磁盘慢或客户端卡住时，首句、回执和取消会一起受影响。将 UI 广播改成有界队列，并用单写入者批量持久化；关键最终回执保留立即落盘语义。当前命令锁也不等于完整的事件顺序机制。 |
| P2 | services/agent/storage.py；services/tts/service.py；services/tts/worker.py | events/utterances 没有时间/容量清理，TTS 的取消集合与 generation token 字典也长期保留。运行时 utterances 已加上限，但其余数据需要生命周期清理和长时间运行测试；不要删除仍在推理/队列中使用的取消 token。 |
| P2 | native/windows/win32.py: image；native/windows/desktop.py: capture；apps/desktop/electron/main.ts: connectRuntime | 最多 3,500 万像素的单张截图，与 12 张快照上限及 32 MiB WebSocket 包预算没有统一容量约束。极大或高熵窗口可能占用大量内存/导致连接失败。建立图像字节和总内存预算，缩放时保留正确坐标变换；发送到模型前验证截图新鲜度。 |
| P2 | services/agent/config.py: update/public；packages/protocol/events.py；packages/protocol/speech-events.schema.json | voice/stt 深层字段、若干布尔选项和错误类型尚未形成完整配置 schema；public 只过滤顶层敏感字段。模型输出 schema、实际校验和 TypeScript 宽泛事件类型也可能漂移。优先集中配置验证和敏感字段过滤，再为工具/动作/事件建立共享版本化契约。路径排除不能保证识别源码中硬编码的所有秘密。 |
| P2 | services/agent/runtime.py: _speech_worker/_turn/_execute | TTS 失败时 speaker 返回后仍可能发 task.state=idle；确认执行后的结果保存在事件账本，但没有完整纳入下一轮模型事实上下文。应分别表达文字生成与语音失败，并把已确认操作结果作为有界、带状态的模型证据输入，避免模型仅看到自己提议的动作。 |
| P2 | services/tts/adapters/sovits.py；scripts/package_backend.py；pyproject.toml | 本地引擎适配依赖 GPT-SoVITS 内部 API，记录 revision 但不强制匹配兼容版本；Python 依赖以范围声明，打包还直接复制开发环境 site-packages。建议建立经过验证的引擎/依赖清单、干净打包环境和版本矩阵。音色/模型资源仍属于外部交付。 |
| P3 | apps/desktop/renderer/App.tsx；services/agent/runtime.py | 两个模块同时承担较多 UI/会话/工具/语音职责，长 JSX 行和字符串事件分支增加修改成本。按现有职责逐步拆分设置表单、录音、工具控制与回合协调；无需一次性重写。 |

建议先处理事件写入与容量生命周期，再统一契约与发布依赖，最后拆分大模块。单用户本机产品目前保留模块化单体和独立推理进程更合适；没有证据支持增加分布式服务。
